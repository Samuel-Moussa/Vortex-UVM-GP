# riscvISACOV — per-instruction reference

**What this file is.** The riscvISACOV coverage model activates one covergroup per
RISC-V instruction. This document lists every one of the 80 covergroups this project
actually builds and runs — what the instruction does, what the covergroup checks
*in this project's build specifically* (not the vendor's full theoretical catalog —
see §1), and its current measured status in the banked
`vortex_uvm_env/cov/isacov_gaphunt/merged_excl_isa.ucdb` (2026-09-20, after the
round-3 gap-hunt: 477/481 = 99.17%, see `RISCVISACOV_STATUS.md`).

Source of truth for every row: `third_party/riscvISACOV/source/coverage/
RV32I_coverage.svh` (RV32I, Imperas-authored, unmodified) and
`Vortex/sim/uvmsim/isacov/ext/coverage/RV32{M,Zicsr,F,Zifencei}_coverage.svh`
(generated by this project from Imperas' own dvplan CSVs — see
`RISCVISACOV_GENERATOR.md`). Status column cross-checked directly against the
banked UCDB (`vcover report -cvg -details`), not assumed from prose.

## 1. What's actually exercised — read this before the tables

riscvISACOV supports a much larger coverpoint catalog than this project builds.
Coverpoint *types* are gated by `COVER_LEVEL_*` macros
(`RISCV_coverage_common.svh:65-95`), and `compile.sh:211` sets only
**`+define+COVER_LEVEL_BASIC`**. That macro cascades to exactly four active
coverpoint families — everything else in the vendor source (register-*value*
buckets, bit-toggle coverage, `rd==rs1`-style hazard crosses, divide-by-zero
classification, FP rounding-mode coverage, CSR field-level coverage) is
`` `ifdef ``-compiled OUT and contributes zero bins to any bank this project has ever
produced. Quoting a vendor doc or a generic riscvISACOV description that mentions
those richer coverpoints as if they were active here would be wrong for this build.

The four active families, and what each one means:

| coverpoint | active for | what it asks |
|---|---|---|
| `cp_asm_count` | every instruction | "did the exact mnemonic string retire at least once?" — a single boolean bin, keyed on disassembly text matching (`RV32I_coverage.svh` etc., `bins count[] = {1}`) |
| `cp_{rd,rs1,rs2,fd,fs1,fs2}_reg_assign` | every instruction with that operand | "which architectural register (x0–x31 / f0–f31) was used?" — excluded from this project's headline ISA-behaviour metric as a **methodology decision** (EOTH class, `isacov_exclude.do`), not a stimulus gap: it's ~92% of the raw bin space and measures the compiler's register allocator, not the DUT (see `RISCVISACOV_STATUS.md` §6c) |
| `cp_{rd,rs1,rs2}_sign` | integer-register instructions only — **never present for RV32F's `fd`/`fs1`/`fs2`** (confirmed: `grep -c cp_fd_sign RV32F_coverage.svh` → 0) | "was the register's 32-bit content negative, positive, or exactly zero?" (`int32_t'(rd_val)` etc.) |
| `cp_imm_value` / `cp_csr_value` | instructions with an immediate or CSR operand | "was the parsed immediate/operand text negative, positive, or exactly zero?" — **both are the identical expression** `int'(ins.current.imm)`; `cp_csr_value` is just a differently-named copy of the same coverpoint on CSR instructions, not a separate measurement (see §4) |

**Consequence for RV32F specifically:** no sign or value coverpoint exists for an
*FP* register at all in this vendor source (`grep -c cp_fd_sign RV32F_coverage.svh`
→ 0) — `cp_rd/rs1/rs2_sign` only ever appears on an *integer* operand. That means
18 of RV32F's 26 instructions (the pure float-to-float ops: `fadd.s` … `fclass.s`)
have **only** `cp_asm_count` active (ceiling 1/1), while the other 8 — the ones
with a genuine integer-register or immediate operand (`fcvt.w.s`/`fcvt.wu.s`,
`fcvt.s.w`/`fcvt.s.wu`, `fmv.x.w`/`fmv.w.x`, `flw`, `fsw`) — additionally get a
sign or `cp_imm_value` coverpoint on that integer side (ceiling 4/4: asm_count +
3-bin sign/imm). Verified directly against each of those 8 covergroups' source,
not assumed from the pattern.

**`cp_illegal_inst`** exists in every covergroup but samples only `iff (ins.trap==1)`
— Vortex has no trap architecture (`rvvi.trap[h][0] = 1'b0` hardwired,
`vortex_rvvi_shim.sv:113`), so this coverpoint can never sample on this DUT and
contributes zero bins either way. Not counted, not waived — structurally inert.

**Not in this table: `nop`.** `rv32i_nop_cg` is one of the vendor's 39 RV32I
covergroups, but it's excluded wholesale (EUR class, cited `OBS-050`/`OBS-056`):
`nop` is purely a disassembler-side pseudonym for `addi x0,x0,0`, and this
project's map generator deliberately disassembles with `-M numeric,no-aliases`
(required for every *other* covergroup's register-numbering to work at all), so
the literal string `"nop"` can never appear in any map this pipeline produces.
The encoding itself executes correctly and is counted under `addi_cg`.

## 4. RV32Zicsr — 6 instructions (control/status register access)

Every CSR instruction (register-form and immediate-form alike) checks
`cp_csr_value` — but this coverpoint is **wired to the wrong trace field** in the
vendor source and does not measure what its name implies (evidence:
`RV32Zicsr_coverage.svh:70` reads `int'(ins.current.imm)`; `add_csr()`
(`RISCV_instruction_base.svh:485-486`) writes the CSR address into `imm2`, never
`imm` — the address is never what this coverpoint samples). Concretely:

- **Register-form** (`csrrw`/`csrrs`/`csrrc`): nothing ever populates `.imm`, so
  it stays at its default 0 — only the `zero` bin can ever fire, `neg`/`pos` are
  permanently excluded (EUR) regardless of what CSR or value is targeted.
- **Immediate-form** (`csrrwi`/`csrrsi`/`csrrci`): `.imm` IS populated, but with
  the instruction's own 5-bit **unsigned** `uimm` operand (0–31) — `neg` is
  excluded on the same unsigned-field reasoning as `slli`'s shift amount.

Full trace and reasoning: `isacov_exclude.do` (EUR class, CSR-value block).

| Instr. | What it does | What's checked (beyond `cp_csr_value`, above) | Status |
|---|---|---|---|
| `csrrw` | t = CSR; CSR = rs1; rd = t (atomic swap) | asm_count · rd/rs1 sign | 8/8 ✅ |
| `csrrs` | t = CSR; CSR = t \| rs1; rd = t (atomic set) | asm_count · rd/rs1 sign | 8/8 ✅ — `rs1_sign/neg` needed a dedicated forced call (register-form CSR traffic elsewhere in the corpus never uses a negative-valued mask register) |
| `csrrc` | t = CSR; CSR = t & ~rs1; rd = t (atomic clear) | asm_count · rd/rs1 sign | 8/8 ✅ |
| `csrrwi` | t = CSR; CSR = zimm; rd = t | asm_count · rd sign · imm(uimm) value | **7/8 — 1 bin OPEN.** `rd_sign/neg` (old CSR value negative before the write) did not close despite an `mscratch`-seeding sequence identical to the one that worked for `csrrsi` — root cause not found; lockstep byte-exact on the run rules out a DUT bug, most likely a code-generation/sequencing detail not yet isolated |
| `csrrsi` | t = CSR; CSR = t \| zimm; rd = t | asm_count · rd sign · imm(uimm) value | 8/8 ✅ — closed via a forced `mscratch` (`CSR 0x340`, the one genuinely full-width read/write CSR on this RTL — `fflags`/`frm` are sub-32-bit and can never carry a sign) write-then-read sequence |
| `csrrci` | t = CSR; CSR = t & ~zimm; rd = t | asm_count · rd sign · imm(uimm) value | **7/8 — 1 bin OPEN.** Same `rd_sign/neg` gap and same open root cause as `csrrwi` |

**Why `mscratch` and not `fflags`/`frm`.** Every pre-existing CSR stimulus in this
suite (`csr_probe`, `sfu_masks`) targets `fflags`/`frm` — real, architecturally
meaningful FP-control CSRs, but both sub-32-bit
(`VX_csr_data.sv:102-104,172-174`), so they can never produce a negative
`cp_rd_sign`/`cp_imm_value` reading regardless of stimulus. `mscratch`
(`VX_CSR_MSCRATCH = 12'h340`, `VX_types.vh:57`) is the one CSR in this RTL that's
genuinely full-XLEN read/write (`VX_csr_data.sv:147,176`) — used here *only* to
exercise these coverage corners, never for any architectural purpose, and gated
to a single thread (`tid==0`) because `mscratch` is one scalar register shared by
every thread in a core, not per-warp/per-thread state.
